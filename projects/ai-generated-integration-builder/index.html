01 / Product thesis

Help developers build integrations faster without giving up control.

Enterprise SaaS platforms need connectors for many vendors. Rebuilding authentication, API clients, data mappings, retries, pagination and logging for each vendor consumes engineering effort. The proposed developer studio turns validated API evidence into review-ready TypeScript packages rather than promising fully autonomous production deployment.

Primary user · Integration developer

Create, inspect, edit, test and own custom connectors.

Governance user · Engineering lead

Review capabilities, access scopes, quality and security before release.

Value hypothesis

Reduce repetitive connector scaffolding while retaining human accountability and explicit evidence for supported capabilities.

02 / Problem discovery

Four recurring pain points shape the MVP.

Repeated API plumbing

Different providers require custom authentication, pagination, retries and logging.

Client-rendered documentation

Legitimate API portals may not expose machine-readable documentation to simple extraction.

Ambiguous activity semantics

User inventories and scheduling events do not prove login history, paid seats or billed usage.

Verification and recovery

Missing files, malformed responses and unsafe redirects need visible checks and safe retry paths.

04 / Agentic architecture

Evidence-first orchestration with three approval gates.

React and TypeScript frontend, Express APIs, a checkpointed state machine and a server-side model registry. API capabilities are classified as documented, derived or unavailable before scopes and mappings are finalized.

Phase 01API evidence

Validate URL, docs and OpenAPI

Phase 02Capability & plan

Classify evidence, map data and approve capabilities

Phase 03Generation

Auth, client, user/activity, resilience; approve scopes

Phase 04Review & export

Security, tests, code review and ZIP

The current repository describes an eight-stage workbench including the orchestrator; the attached five-slide deck summarizes an earlier seven-agent demo. Three mandatory human approvals are common to both.

Human control

Capability approval, authentication and scope approval, and code review.

Model boundary

Deterministic demo engine is labeled simulated; real Gemini requires server configuration.

Observability

Redacted trace events, retry recovery, static checks and versioned code artifacts.

Security by design

HTTPS and SSRF protection, default connector immutability, creator-scoped ownership and server-side secrets.

05 / MVP decisions

Narrow the scope to trusted read-only REST integrations.

In scope

Catalog, onboarding, custom connector definition, API evidence validation, user/activity retrieval, TypeScript generation, editable code and ZIP export.

Out of scope

Automatic production deployment, unrestricted runtime code execution, unsupported data semantics and arbitrary connector languages.

Product decision

Unverified usage data is labeled rather than invented. Calendly scheduled events represent a derived scheduling-activity proxy, not login or license utilization. Sandbox fixtures are simulated.

06 / Evaluation strategy

Make quality visible before expanding the MVP.

The supplied presentation reports a Calendly demonstration with three approvals, 15 generated TypeScript files and six of six automated test groups passed. These are reported prototype results, not independently rerun here or customer outcomes.

Proposed quality metrics

Documentation grounding, capability classification accuracy, required file completeness and security-check pass rate.

Proposed efficiency metrics

Time to review-ready connector, manual editing effort, retry recovery rate, generation latency and model cost.

Measure proposed indicators against a manual integration-development baseline; do not claim production ROI until validated.
